# 휠 스크롤·쇼츠 선택 속도 개선 검증 (2026-10-17)

## 원인과 변경

- 쇼츠 목록/후킹 패널의 `overscroll-behavior-y: contain`이 패널 끝에서도 휠 입력을 가로챘다. 내부 스크롤은 유지하고 끝에서는 페이지로 전달하도록 변경했다.
- 상태 조회와 각 미디어 요청이 되돌리기 이력까지 포함한 프로젝트 JSON을 반복해서 읽었다. 조회에는 이력을 제외한 현재 상태를 메모리에 보관하고 독립 사본을 반환한다. 저장·외부 파일 변경 시 갱신하며 편집/되돌리기는 기존 전체 데이터를 사용한다.
- 쇼츠 선택만 바뀔 때 전체 영상 타임라인과 쇼츠 목록을 다시 생성하지 않고 선택 표시만 바꾼다. 정기 상태 갱신도 내용이 같은 목록의 초점/스크롤/이미지를 유지한다.
- 후킹 이미지는 문구·강조·글자 크기 기준으로 최대16개 재사용한다. 원본 컷/설명 썸네일 주소도 관련 없는 편집마다 바뀌지 않는다. 수동 미리보기 재시도는 캐시를 우회한다.
- 영상 프레임 갱신에서 레이아웃 크기를 먼저 읽어 표시선 변경 직후의 강제 레이아웃 계산을 줄였다.

## 측정

- 실제 사용자 데이터11개 프로젝트, 동일 응답2,634,540바이트의 `/api/state`를 서버 교체 전후 각각5회 조회한 중앙값: **274.35ms → 68.97ms**. 새 서버 최초 로딩을 마친 뒤 측정했다.
- 별도 저장소 조회 측정에서 가장 큰 프로젝트(이력 포함20.7MB)는 전체 읽기128.7ms, 현재 상태 재사용2.9~3.3ms였다. 이는 데이터 읽기 시간이며 쇼츠 클릭부터 화면 표시까지의 전체 시간은 아니다.
- 최초 접근이나 편집 직후에는 JSON을 다시 읽는다. 영상 디코딩/아직 생성되지 않은 썸네일 준비/AI 작업 시간은 이번 수치에 포함하지 않는다.
- 로컬 측정 결과: `data/verification/scroll-speed-20261017/production-benchmark.json`.
